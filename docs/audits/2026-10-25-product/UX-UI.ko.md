> 사용자가 지정한 UX/UI 원본 보고서의 열람용 사본입니다. 별도 분석 채팅의 파일 작성 기록과 후속 수정 기록에서 원문을 복원했습니다. 본문 판단은 변경하지 않고 코드 링크만 분석 커밋에 고정했습니다. 원본이 참조하는 스크린샷·로그·재현 파일은 이번에 가져오지 못했으며 해당 위치를 본문에 표시했습니다.

**핵심 판단: 현재 ro.bot의 주요 장애물은 화면의 미적 완성도보다 ‘입력 → 확인 → 결과 → 복구’ 사이의 단절이다.**

2026-10-25 검토. 대상은 `/workspace/ro.bot`, 커밋 `23b38f56fa4f82390d721b70654acfa9e7c8b273`. 제품 코드·기능·설정은 수정하지 않았다. 분석 스크립트·스크린샷·합성 데이터만 별도로 만들었다. 검토 전후 Git 작업 트리는 깨끗했다.

승인 전 전송 차단, 변경된 파일의 이동 차단, 파일 이동 후 복원은 확인됐다. 그러나 사용자가 확인해야 할 내용이 잘리거나, 답변·취소가 다른 탭에 숨거나, 실패가 정상 빈 상태로 바뀐다. 따라서 **기존 기능의 완료·검토·복구 가능성을 먼저 개선할 근거가 있다.** 실제 이용자에게 얼마나 자주 발생하는지는 모른다. 아래의 ‘확인’은 재현한 구현 동작이며, 이용자 피해 규모·이탈률을 확인했다는 뜻이 아니다.

가장 먼저 다룰 다섯 가지는 F03 기록 입력 소실·오류 상태 왜곡, F02 답변·취소의 위치 및 복귀 상태, F04 전송 미리보기 누락, F07 파일 승인 목록 누락, F06 검색 근거의 불완전한 열기다. 모두 핵심 과업의 성공 조건과 직접 연결된다.

**F01 — 준비가 안 된 상태를 ‘기록이 없는 상태’로 보여 준다.**

- **직접 원인 / 근본 가설:** 코어가 반환한 `(id, 이유)`를 펫이 개수로 축약한다 / 성공 알림을 중심으로 설계해 부분 성공을 별도 상태로 다루지 않은 것으로 보인다.
- **최소 개선·제약:** 처리한 배치·미처리 파일·사유·다음 행동을 접을 수 있는 결과로 남긴다. 실패가 있으면 사용자가 닫을 때까지 유지한다. 자세한 파일 이름 노출과 화면 공간이 늘어나므로 기본 요약과 상세를 구분한다.
- **검증·반박:** 파일 변경·복원 위치 충돌·쓰기 권한 부족을 각각 만들어 비개발자가 ‘미처리 대상과 안전한 다음 행동’을 지목할 수 있는지 본다. 표시 원인과 실제 파일 상태가 일치해야 한다.

**T4 — 확인할 일과 접근성·작은 화면에서의 과업 수행을 평가했다.**

**F10 — ‘확인할 일’은 알리지만 무엇을 해야 하는지 열 수 없다.**

- **사용자·상황:** 로컬 설정 파일의 권한이 과도하거나 내부 감사 문제가 발견된 사용자.
- **재현·관찰:** 격리된 합성 `config.json` 권한을 0644로 설정 → 서버는 ‘권한 과다 … config.json’ 반환. UI는 ‘확인할 일이 있어요’, 숫자 1, 초기화만 보여 준다. 숫자는 버튼이 아니며 어디가 문제인지 열 수 없다. 일반 읽기 권한 거부를 재현한 것이 아니라 **감사 경고의 전달**을 재현한 것이다.
- **근거:** 감사 경고 화면 (원본 첨부: `/workspace/scratch/ux-audit/13-audit-attention.png`, 이 브랜치에는 미포함), [상세 생성](https://github.com/rhochoi/ro.bot/blob/23b38f56fa4f82390d721b70654acfa9e7c8b273/ro/pet.py#L537), [상태 응답](https://github.com/rhochoi/ro.bot/blob/23b38f56fa4f82390d721b70654acfa9e7c8b273/ro/pet.py#L598), [화면의 집계만 표시](https://github.com/rhochoi/ro.bot/blob/23b38f56fa4f82390d721b70654acfa9e7c8b273/ro/pet.py#L3034).
- **영향:** 경고가 반복되어도 해결할 수 없고, ‘초기화’를 복구로 오해할 가능성이 있다. 문제의 실사용 발생 빈도는 모른다.
- **직접 원인 / 근본 가설:** 상태 응답의 상세와 status_line을 화면이 소비하지 않는다 / 시각적 주의 신호와 사용자의 다음 행동이 연결되지 않은 것으로 보인다.
- **최소 개선·제약:** 확인할 일에서 기존 상세 메시지와 `ro audit` 등 적절한 진단 경로를 보여 준다. ‘초기화’는 실제 동작에 맞게 ‘답변/알림 닫기’로 표현한다. 경로 노출이 늘지만 외부 전송은 필요 없다. 권한 자동 수정은 하지 않는다.
- **검증·반박:** 서로 다른 감사 원인 두 개를 주입하고 사용자가 원인과 다음 행동을 구별할 수 있는지 본다. ‘닫기’가 문제 해결과 다름을 이해해야 한다.

접근성은 자동 검사와 과업 수행을 분리했다. axe-core 4.10.3으로 라이트/다크 × 네 탭을 검사했다. 8상태 중 양 테마의 긴 타임라인에서 `scrollable-region-focusable` 경고가 나왔다. **그러나 수동 키보드 검사에서 Chromium은 타임라인을 Tab 순서에 넣었고, 해당 영역에 포커스한 뒤 PageDown으로 scrollTop이 0→230이 됐다.** 따라서 이 결과를 ‘키보드 스크롤 불가’ 확정 결함으로 올리지 않는다. WKWebView에서는 재확인이 필요하다. 자동 결과 (원본 첨부: `/workspace/scratch/ux-audit/followup.json`, 이 브랜치에는 미포함), 수동 결과 (원본 첨부: `/workspace/scratch/ux-audit/keyboard.json`, 이 브랜치에는 미포함).

- 확인한 장점: 주 입력의 포커스 스타일, 팔레트의 방향키/Enter/Esc·포커스 복원, 회상·정리 메시지·토스트의 live region, 동작 줄이기에서 CSS 애니메이션 0개, 두 테마의 검사 대상에서 대비 위반 미검출.
- 과업상 확인한 문제: F09의 포커스 중 토스트 제거. 선택 시간을 제한하고 작업 위치를 잃게 한다.
- 코드상 확인할 과제: 탭의 활성 상태는 CSS class로만 변경되고 aria-current/selected가 없다. 엔진 답변 카드에는 live region이 없다. 접힌 펫은 클릭 가능한 div이고 role/tabindex가 없지만 ⌥R 대체 진입은 실제 작동했다. 따라서 ‘키보드로 진입할 방법이 전혀 없다’고 판단하지 않는다. VoiceOver가 선택 탭·완료·취소·근거 링크를 어떻게 읽는지는 미확인이다.
- 타깃 크기는 홈 탭 약 26×21px, 닫기 20×20px, 보내기 26×26px, 입력 글자 11.5px였다. 이는 저시력·손 조작 사용자의 검증 항목이다. 간격 예외와 실기기 조작을 검증하지 않아 수치만으로 WCAG 실패를 확정하지 않았다.

모바일은 주 제품 목적이 확인되지 않았다. 브라우저 320×568에서는 패널 폭이 292px로 줄어 가로 넘침이 없었다. 320×300으로 높이를 줄이면 입력이 말풍선 경계를 약 14px 벗어났다(화면 (원본 첨부: `/workspace/scratch/ux-audit/21-small-height.png`, 이 브랜치에는 미포함)). 입력 자체는 보였으므로 과업 불능으로 단정하지 않는다. 실제 iOS/Android 가상 키보드, 핀치 확대, 터치 드래그, 200% 텍스트 확대는 미검증이다. 모바일 지원을 확대하기보다, 지원 화면 크기와 저시력 확대 환경을 정하고 최소 높이·내부 스크롤을 검증하는 것이 작은 개선이다. 네이티브 창은 [360×530 고정 확장 크기](https://github.com/rhochoi/ro.bot/blob/23b38f56fa4f82390d721b70654acfa9e7c8b273/ro/pet_mac.swift#L360)를 사용한다.

**우선순위는 사용자 영향·재현 근거·확신도·상대 비용으로 정했다.**

**검증 계획은 결론을 바꿀 수 있는 최소 사용자 관찰로 시작한다.**

첫 라운드는 **6명, 각 35~45분**이면 충분하다. 표본이 작으므로 빈도나 통계적 유의성을 추정하지 않는다. 제품을 쓰려는 Mac 사용자이며 본인이 쓰는 엔진 CLI가 하나 있는 사람을 모집하되, ro 첫 사용자 3명과 로컬 비서/CLI 숙련자 3명을 섞는다. 이 중 2명은 평소 키보드를 주로 사용하고, 가능하면 1명은 VoiceOver 또는 확대 기능을 실제로 사용하는 사람으로 모집한다. 접근성 사용자 확보가 안 되면 보조기술 검증은 완료로 표시하지 않는다. 역할에 맞는 실제 운영체제와 WKWebView 빌드를 사용한다.

5/6·시간 기준은 개선 여부를 판단하기 위한 사전 운영 기준일 뿐 통계 추정치가 아니다. 사용자 테스트에서 어려움이 관찰되지 않아도 입력 소실·표시/저장값 불일치 같은 재현 가능한 결함을 부정하는 증거로 쓰지 않는다. 반대로 단순히 특정 화면이 마음에 들지 않는다는 선호만으로 우선순위를 올리지 않는다.

개선안을 구현하게 될 다음 단계에서는 각 F의 재현 조건을 그대로 회귀 기준으로 쓴다. 보존할 동작은 무승인 외부 호출 0회, 동일 승인 ID 재사용 거부, 변경된 파일 이동 0건, 승인한 합성 파일만 이동, 되돌리기 후 경로·내용·권한 일치다. 실제 원본 이벤트가 나중에 제공되면 먼저 수집 누락·대상 사용자·분모를 확인하고, `미리보기→승인→결과 확인`, `기록→회상→근거 열기`, `정리 제안→적용→부분 실패→복원`의 이탈과 반복을 교차 확인한다. 현재 로그에 화면 노출/클릭 이벤트가 없다는 점도 고려해야 한다. 이 분석 단계에서는 추적 코드를 추가하지 않았다.
