# ro organize 설계안 — 파일을 읽고 분류·이름 정리

작성: 2026-10-22 · 상태: **O1~O3 구현됨**(`ro/organize.py`), O4~O6 미착수. 결정 ①은 로컬 LLM 없이, ②③은 기본값으로 진행.

## 1. 목표와 완료 조건

`~/Downloads` 같은 폴더의 파일을 **내용까지 보고** 카테고리 폴더로 옮기고, 이름을 일관된 형식으로 바꾼다.
단, 지금의 `ro tidy`와 같은 안전 약속을 지킨다: **제안 → 내가 승인 → 이동(삭제 없음) → 언제든 되돌리기.**

완료 조건(1차): `~/Downloads`에서 계획 생성 → 일부 승인 → 이동·이름변경 → `undo`로 원상복구까지 한 사이클이
실제로 돌고, `ro eval`에 organize 안전 항목이 PASS.

## 2. 현재 상태 (확인한 사실, 2026-10-22)

- 정리가 필요한 파일은 대개 `~/Downloads` 최상위에 몰려 있다(PDF·docx·이미지·html·zip·xlsx·hwp 순으로 많은 편)
  → **1차 대상은 Downloads 하나로 충분.**
- 로컬 LLM 실행기(ollama 등)는 기본 설치돼 있지 않다고 가정한다.
- 내장 도구로 쓸 수 있는 것: `mdls`(Spotlight 메타데이터), `textutil`(docx/rtf/html→텍스트), `sips`(이미지 정보),
  `swiftc`(PDFKit·Vision OCR 호출 가능). `pdftotext`는 없음.
- 이미 있는 재료: [ro/tidy.py](../ro/tidy.py)의 `check_root`(홈 하위만), `walk`(숨김·비밀·프로젝트 폴더·심링크 제외),
  해시 확인, 격리 이동, `journal.jsonl` 기반 `undo`.

## 4. 핵심 설계 결정

1. **원본 내용은 기기 밖으로 나가지 않는다.** 파일 본문은 로컬에서만 읽는다. 외부 엔진(claude/codex/agy)에는
   파일 내용을 보내지 않는다. 내용 기반 판단이 필요하면 **로컬 모델**만 쓴다(설치는 사용자 승인 사항).
2. **3단 분류기 — 싼 것부터, 확신이 낮을 때만 다음 단계.**
   - L1 규칙: 확장자·이름 패턴·출처(`kMDItemWhereFroms`) — 예: `.dmg/.pkg`→설치파일, `Screenshot*`/`스크린샷*`→스크린샷.
   - L2 메타데이터+텍스트 키워드: PDF 첫 페이지 텍스트(Swift PDFKit), docx/hwpx(zip 내부 XML, 표준 라이브러리),
     `mdls` 제목·작성자·생성일 → 키워드 사전으로 "영수증/청구서/계약/논문/이력서" 등 판정.
   - L3 로컬 LLM(선택): L1·L2 확신도가 낮은 파일만, 텍스트 앞 2KB를 넣어 `{"category","title","date","confidence"}`
     JSON만 받는다. 응답은 데이터로만 파싱(허용 카테고리 목록 밖이면 버림).
3. **실행은 기존 tidy 엔진 재사용.** 이동 대상만 "trash"가 아니라 "카테고리 폴더"로 바뀐다.
   `journal.jsonl`에 (원래 경로, 새 경로, 해시)를 남기고 `undo`는 해시 확인 후 원위치. 영구 삭제 없음.
4. **이름은 바꿔도 확장자·내용은 절대 안 바꾼다.** 형식(기본안): `YYYY-MM-DD_<제목>.<ext>`
   - 날짜: 문서 내 날짜 > 메타데이터 생성일 > 파일 수정일 순.
   - 제목: 40자 이내, 파일명에 못 쓰는 문자 제거, **숫자열 6자리 이상(계좌·주민번호 의심)은 빼고**, `log.redact` 통과.
   - 충돌 시 `_2`, `_3`. 원래 이름은 journal에 보존.
5. **학습 연결.** 계획에서 내가 카테고리·이름을 고치면 그 수정이 로그에 남고, 같은 수정이 반복되면
   `ro learn` 후보("'청구서' 키워드 PDF는 재무/청구서로")가 된다. 승인한 것만 L1 규칙에 추가.

## 5. 카테고리 (기본안 — Downloads 구성 기준)

```
~/Documents/정리됨/            ← 대상 루트(결정 필요 ②)
  문서/        일반 pdf·docx·hwp
  재무/        영수증·청구서·견적서·세금
  계약·서류/    계약서·신청서·증명서
  학습·자료/    논문·강의자료·보고서
  표·데이터/    xlsx·csv
  이미지/      png·jpg (스크린샷/ 하위)
  웹페이지/     저장한 html
  압축·설치/    zip·dmg·pkg
  기타/
```
분류가 확실하지 않은 파일(확신도 < 0.6)은 **옮기지 않고 "검토 필요"로만 표시**한다.

## 6. 흐름과 명령

```
ro organize scan  --root ~/Downloads        # 읽기 전용 → ~/.ro/organize/plan.json
ro organize show  [--category 재무]          # 표로 보기: 현재 이름 → 새 위치/새 이름, 근거, 확신도
ro organize edit  ID --category 문서 --name "2026-09-01_전세계약서"
ro organize apply ID [ID...] | --category 재무 # 지정한 것만 이동
ro organize undo  [BATCH]                     # 원위치
```
- 펫 연동(후순위): 말풍선에 "Downloads 정리안 23건" → 카테고리별 승인 버튼(기존 쓰기 승인 게이트 재사용).

## 7. 안전 규칙 (tidy에서 상속 + 추가)

- 상속: 홈 하위만, `~/.ro` 제외, 숨김·비밀 이름·프로젝트 폴더·심링크 제외, 계획 이후 바뀐 파일 건너뜀, 삭제 없음.
- 추가:
  - 최근 10분 내 수정된 파일과 `.crdownload`·`.part`·`.download`(다운로드 중) 제외.
  - iCloud 자리표시 파일(`.icloud`)은 읽지 않음(내려받기를 유발하므로).
  - 텍스트 추출은 파일당 앞 2KB·첫 2페이지만, 추출 결과는 디스크에 저장하지 않음(계획 파일에는 제목·카테고리·근거 요약만).
  - 계획·로그의 근거 문구도 `log.redact` + 숫자열 마스킹.
  - `ro eval`에 3개 항목 추가: scan은 파일을 안 바꿈 / 원문이 엔진 호출로 나가지 않음 / apply→undo 후 원상태.

## 8. 단계 (각 30분 내외)

| 단계 | 내용 | 종료 조건 |
|---|---|---|
| O1 | L1 규칙 분류 + `scan`/`show` (이동 없음) | Downloads 계획이 나오고 파일 변화 0 |
| O2 | L2 텍스트·메타데이터 추출(PDFKit 헬퍼, docx/hwpx zip, mdls) + 이름 제안 | PDF·docx 샘플에서 날짜·제목 추출 테스트 통과 |
| O3 | `apply`/`undo`/`edit` (tidy journal 재사용) + eval 3항목 | 임시 폴더에서 apply→undo 원상복구 테스트 |
| O4 | 실제 Downloads에서 소량(예: 재무 5건) 승인 적용 | 사용자 확인 후 undo 가능 상태 확인 |
| O5 (선택) | L3 로컬 LLM — Ollama + 소형 모델(메모리 16GB에서도 도는 3~4B급) | 설치 승인 후, 저확신 파일만 재분류해 정확도 비교 |
| O6 (후순위) | 수정 → learn 후보, 펫 승인 버튼 | 후보 → 승인 → 다음 scan에 반영 |

## 9. 결정 필요

1. **로컬 LLM(L3) 도입 여부** — Ollama 설치는 시스템 변경이라 승인 필요. 없이도 O1~O4는 동작(규칙+키워드).
2. **정리 대상 루트** — `~/Documents/정리됨/` 신설 vs Downloads 안에 카테고리 폴더 생성.
3. **이름 형식** — `YYYY-MM-DD_제목` (한글 유지) 기본안 그대로 vs 다른 형식(영문 소문자·하이픈 등).

## 10. 남은 위험

- 키워드 분류는 애매한 문서(제목 없는 스캔 PDF 등)에 약하다 → "검토 필요"로 남기고 옮기지 않는 것으로 대응.
- 스캔 이미지 PDF는 텍스트가 없어 OCR(Vision)이 필요 — O2 범위 밖, 필요 시 추가.
- `.hwp`(바이너리 OLE)는 표준 라이브러리로 본문 추출이 어렵다 → 메타데이터·파일명만 사용.
- 이름 변경 후 다른 앱의 최근 파일 목록·링크가 끊길 수 있다 → undo로 복구 가능, 카테고리 단위로 소량씩 적용 권장.

## 11. 구현 메모 (O1~O3, 2026-10-22)

- 대상은 **루트 최상위 파일만**이다. 하위 폴더는 사용자가 묶어 둔 단위라 흩뜨리지 않는다.
- PDF 본문·제목은 macOS PDFKit을 JXA(`osascript -l JavaScript`)로 읽는다. 설치·컴파일 없이 동작한다(스캔 이미지 PDF는 텍스트가 없어 이름·메타데이터만 쓴다).
- macOS 파일 이름은 한글이 NFD(자모 분해)라 판단 전에 NFC로 정규화한다. 실제 이동은 원래 경로로 한다.
- 이름 후보 순서: 파일 이름 → 메타데이터 제목 → 본문 첫 줄 → 짧은 원래 이름 → `제목없음`.
- `ro eval`에는 3개 대신 1개 묶음 항목(읽기 전용·본문 미저장·엔진 미호출·검토 보류·복원)을 추가했다.
  키워드 분류는 본문 약한 일치(예: 진행 보고 문서가 본문의 '계약서'로 계약·서류)로 빗나갈 수 있어, 적용 전 `show`로 확인하고 `edit`로 고친다.
- 검토 후 수정(2026-10-22): URL 인코딩 이름 디코딩, 버전 번호 점 유지(`v2.0`), 빈 괄호 제거, 원본이 사본보다 먼저 깨끗한 이름을 받음, 겹친 사본 표시(`(1) (1)`) 제거.
  복구·백업 코드·OTP·시드 이름은 목록에서 빼고 내용도 읽지 않는다. 분류 기준(본문 키워드 2개면 세분)은 그대로 둔다.
